# 项目文档优先

把目标项目内已有的 Markdown 文档当作获取项目上下文的第一层入口。`AI_readme.md` 仍是 AI 导航和约束信息的优先来源，但不是唯一来源；还要根据当前问题阅读 `README.md`、架构说明、贡献指南、接口说明、开发笔记等有效 `.md` 文档。只有 Markdown 信息不足时，才定向查看其他文件；不要一开始就通读整个仓库或整棵源码树。

## 入口文档发现

1. 确定用户要求处理的目标路径。若用户给出的是子目录，优先把该子目录作为项目范围；只有在需要确认项目边界时，才向上检查祖先目录中的 `.git`、构建清单或包管理文件。
2. 在目标路径的根部先搜寻 Markdown 文件，优先级如下，允许文件系统大小写差异，但写入时使用规范名称：
   - `AI_readme.md`：AI 优先阅读的项目地图、约束和推荐阅读顺序。
   - `README.md`：面向人的项目说明、使用方式和开发入口。
   - 其他与当前问题相关的 `.md`，例如 `ARCHITECTURE.md`、`CONTRIBUTING.md`、接口/设计说明、开发笔记和目录下的项目文档。
3. 评估 Markdown 是否“有效”：能够提供项目目的、范围、结构、入口、命令、依赖、约束、架构、数据流或当前问题相关信息的内容才算有效；纯变更记录、自动生成索引或与当前项目无关的文档不能替代入口信息。
4. 只在根部没有足够有效信息时，查找目标路径下更深层的 Markdown 文件；排除 `.git`、`node_modules`、`vendor`、`dist`、`build`、缓存和生成目录，并选择离目标路径最近、属于当前项目且与任务相关的文档。
5. 若目标是多项目仓库，使用“当前子项目最近的 Markdown 文档 + 仓库根部的共享文档”组合，不要把其他子项目的 README 当成当前项目的入口。

可使用类似下面的只读搜索，随后按文档类型、任务相关性、路径距离和项目边界筛选结果：

```powershell
rg --files -g '*.md' -g '!**/.git/**' -g '!**/node_modules/**' -g '!**/vendor/**' -g '!**/dist/**' -g '!**/build/**' <target-path>
```

## 阅读顺序

按以下顺序获取项目知识：

1. 如果存在当前项目的 `AI_readme.md`，先完整阅读它，提取项目目的、当前状态、目录地图、入口点、运行/测试命令、依赖和环境、不可违反的约束、已知坑点，以及“推荐阅读”列表。
2. 在 `AI_readme.md` 之后，阅读与当前问题相关的 `README.md` 和其他有效 `.md` 文档。若没有 `AI_readme.md`，就从 `README.md` 或最相关的 Markdown 文档开始；不要因为缺少某一个固定文件名而跳过其他 Markdown 信息。
3. 按 Markdown 文档中的推荐顺序和当前任务相关性，优先读入口、架构、接口、配置说明、核心流程和测试说明。对于很大的文档，只读相关章节。
4. 只有在已有 Markdown 文档无法提供有效答案时，才查看非 Markdown 文件。此时使用定向搜索和最小范围读取，例如用 `rg -n` 搜索函数名、路由、配置键、命令或错误信息，再打开命中的少量配置、清单或源码文件。
5. 不要默认读取所有源码、所有历史提交、所有依赖源码、生成文件或二进制文件。若必须扩大范围，说明 Markdown 信息为何不足、为何需要扩大范围，并保持在当前项目边界内。

## 缺少入口文档时

如果 `AI_readme.md` 或 `README.md` 缺失：

- 对用户已授权的项目开发、修改或整理任务，在目标项目根目录创建缺失的文档；若两者都缺失，就同时创建。
- 对明确的纯只读审阅、问答或状态报告，不要未经授权写入文件；指出入口文档缺失，并在用户允许后补建。
- 如果存在其他有效 `.md`，先阅读并利用这些文档；只有在 Markdown 信息不足时，才通过最小范围的目录列表、项目清单或其他文件收集事实，再写文档。未知内容标成“待确认”，不要凭空补全命令、架构或约束。
- 创建后先阅读 `AI_readme.md`，再继续任务。

`README.md` 至少覆盖：

- 项目用途、面向对象和当前状态
- 快速开始、依赖、环境变量和常用命令
- 主要功能或工作流
- 目录/模块概览
- 开发、测试、构建、部署和常见故障入口

`AI_readme.md` 至少覆盖：

- 项目边界、目的、状态和事实来源
- 入口点、关键目录/模块及其职责
- 推荐阅读顺序（优先列出相关 Markdown 文件，包含文件路径 + 阅读目的）
- 运行、测试、构建命令及前置条件
- 关键依赖、配置、数据流或调用链
- 修改约束、不变量、生成文件/勿手改目录和已知坑点
- 完成任务前应验证的检查
- `Last verified` 或等价的验证时间/范围

## 项目修改流程

在修改代码、配置、文档或数据处理逻辑前：

1. 先读取 `AI_readme.md`（如存在），再读取 `README.md` 和其他相关 Markdown 文档，确认正确的入口、约束和验证命令。
2. 用定向搜索确认改动点及其调用方/测试，不凭文件名猜测影响范围。
3. 做最小必要修改，遵守文档中记录的生成、格式化、迁移和兼容性规则。
4. 按 `AI_readme.md` 的验证清单运行相关测试、检查或构建；若无法运行，记录原因。
5. 若改动影响架构、入口、命令、目录职责、配置、约束或推荐阅读顺序，同步更新 `AI_readme.md`；若改动影响人类使用或开发流程，也更新 `README.md`。
6. 更新文档中的验证时间和已知限制，避免留下与代码不符的导航信息。

## 文档维护原则

- Markdown 文档是 AI 获取项目上下文的第一层来源，`AI_readme.md` 是优先导航文档但不是唯一来源，也不是代码事实本身；先在相关 Markdown 之间交叉核对，仍有冲突或缺口时再查看可验证的配置、清单、源码和测试，并修正文档。
- 保持 `AI_readme.md` 短而可导航：记录“去哪里看、为什么看、如何验证”，不要复制整段源码或大篇幅 API 文档。
- 路径应使用相对于项目根目录的稳定路径，并注明路径用途；不要写只在某台机器上成立的绝对路径或凭空假定的秘密值。
- 推荐阅读列表应按任务导航价值排序，并优先包含入口 Markdown、架构/接口说明、核心流程和测试。
- 如果存在多个入口文档，明确当前文档覆盖的项目范围，并链接到其他子项目入口。
