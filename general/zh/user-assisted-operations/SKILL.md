# 用户协助操作

在任务执行中评估“由 Codex 做”与“由用户手动做”的总成本。目标是让用户只承担少量、明确、容易完成的动作，同时让 Codex 继续完成所有不依赖该动作的工作。

## 判断是否请求用户协助

当出现下载、复制、上传、导出、拖放、登录、授权、提供私有资料、准备大型资源等步骤时，比较以下因素：

- 用户是否能用一到几步完成，而 Codex 需要长时间搜索、传输、反复尝试或重建内容；
- 操作是否依赖用户的账号、浏览器会话、本地路径、私有文件、付费资源或明确授权；
- 自己执行是否会产生明显的 token、网络、计算或失败重试成本；
- 用户手动提供原始资源是否比 Codex 自己仿制、重新下载或重新构建更准确。

满足上述任一明显条件时，准备一个用户协助方案。不要把可由 Codex 低成本、安全完成的普通文件操作、简单检索或小型转换无故转交给用户。

## 推荐工作流

1. 将任务拆分为独立工作和依赖外部动作的工作。
2. 先完成所有不依赖用户动作的分析、代码、文档、目录准备和验证。
3. 在阶段性回复或当前阶段完成后，再请求用户执行高性价比的手动动作；不要在仍有大量独立工作可做时过早停顿。
4. 请求必须具体到可执行：说明要做什么、来源或位置、目标文件名/格式、放置路径或返回方式，以及完成后的确认方式。
5. 同时给出可行选项：优先推荐用户手动完成；如果用户希望，也说明 Codex 可以尝试的替代方案及其成本/权限要求；必要时给出“不提供该资源时如何继续”的降级方案。
6. 用户完成后，先检查文件是否存在、格式是否正确、内容是否可读，再继续剩余任务。
7. 用户暂时不操作时，不要反复催促：如果有低成本替代方案就继续；否则说明当前阻塞点和所需资源。

## 请求内容要求

每次请求尽量只包含一组紧密相关的动作，并包含：

- **已完成**：简短说明当前已经推进的工作；
- **请你操作**：明确的单步或少量步骤；
- **放在哪里/如何提供**：准确的文件名、目标路径、上传方式或回复格式；
- **为什么这样更合适**：例如可避免长时间下载、重复构建或大量 token 消耗；
- **完成标志**：让用户知道回复“已完成”、上传文件或给出路径即可；
- **备用方案**：用户不方便操作时，说明由 Codex 继续处理的代价，或说明暂时无法继续的原因。

可采用以下表达结构：

> 我已完成 A、B。现在 C 由你手动完成会更快：请从【来源】获取【资源】，命名为【文件名】，放到【目标路径】，完成后回复“已放好”即可。我随后会检查并继续 D。若你希望我自己处理，我也可以尝试，但预计会增加【时间/下载/构建/权限】成本。

## 常见场景

- **下载已知资源**：如果用户能直接访问明确链接，建议用户下载并放入指定目录；不要为了一个现成资源花大量时间抓取、解压或重建。
- **复制大型或私有文件**：让用户从其本地位置复制到明确的项目路径，或通过当前可用的上传入口提供；不要猜测用户电脑上的路径。
- **账号、登录和授权**：请用户在自己的浏览器或应用中完成登录/授权，再让 Codex 继续；绝不索要密码、令牌或私钥。
- **用户拥有的素材**：优先请用户直接提供原图、模板、数据、导出文件或截图；不要在已有原始资料时自行仿制导致质量或格式损失。
- **桌面操作**：如果必须由用户点击、选择目录或确认系统弹窗，给出精确动作和后续验证方式。设备连接确认由独立的 hardware-connection-check 技能处理。
- **耗时构建或重复生成**：如果用户已有可复用的构建产物、依赖包、模板或样例，优先请求其放入目标位置，而不是重新构建。

## 边界与安全

- 用户明确要求“由你完成”时，除非缺少权限、资源或存在安全限制，不要擅自改为让用户操作。
- 不要因为操作看起来麻烦就把代码编写、调试或普通低成本命令转交给用户。
- 不要请求密码、私钥、访问令牌或其他秘密；引导用户使用登录、授权、上传或脱敏后的文件方式。
- 不要把需要用户承担风险、付费或对外发布的动作默认为已授权；先说明影响并让用户确认。
- 用户协助请求不应替代进度汇报。先交付当前可交付结果，再说明依赖项、推荐动作和下一步。
